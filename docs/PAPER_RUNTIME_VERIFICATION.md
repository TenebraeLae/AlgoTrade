# Проверка сетевого paper-runtime (M7)

Это эксплуатационная проверка, не сетевой pytest: по `docs/11_TESTING.md`
автотесты работают на фикстурах без внешней сети. Успех FakeGateway не подтверждает
доступность брокера, TLS, актуальность свечей и автономный сетевой цикл.

## Предварительные условия

1. Только `TBOT_TRADING_MODE=paper`. `main` создаёт read-only `InvestGateway` с
   `sandbox_target()`; `PaperCycle`/`PaperBroker` не имеют доступа к этому gateway.
   Live не включать, sandbox-счета и заявки для этой проверки не создавать.
2. Нужен действующий sandbox-токен в OS keyring, сервис `tbot`, имя `broker_token`.
   Ранее раскрытый в переписке токен отозвать; не переиспользовать его.
   Не присылать новый токен в чат, не помещать в `.env`, shell-команду или логи.
   Для скрытого локального ввода можно выполнить из терминала с TTY:

   ```powershell
   .\.venv\Scripts\python.exe -c "from getpass import getpass; from trading_bot.security import get_token; value = get_token('broker_token', prompt=lambda: getpass('Sandbox token: ')); del value"
   ```

   Если запись уже есть, `get_token` использует её, а не заменяет. Управление
   заменой/отзывом секрета выполняет оператор в своём хранилище.
3. Человек задаёт только `TBOT_PAPER_STARTING_BALANCE` — виртуальный начальный
   баланс. Решение оператора 2026-10-16: кандидаты MOEX, ликвидный пул 15–30 и
   проверенный ID настоящего IMOEX определяются автоматически через API, без
   ручного ввода/утверждения. Устаревшие `TBOT_PAPER_CANDIDATE_TICKERS`,
   `TBOT_PAPER_APPROVED_TICKERS`, `TBOT_PAPER_INDEX_ID` для запуска не нужны.
   Недоступный/неоднозначный индекс не заменять ETF или IMOEX2. Та же автоматизация
   обязательна для будущего live, но live этим не разрешён.
4. Проверять в разрешённый будний день календаря, во время обычной сессии,
   лучше после закрытия первого часового бара. Защитные окна запрещены.
   Нужна доверенная TLS-цепочка. Не отключать TLS-проверку при ошибке.
5. Использовать **новую отдельную БД**; не открывать рабочую `data/tbot.db`.
   Отдельный каталог также изолирует heartbeat. Оператор сначала проверяет,
   что выбранный путь действительно новый и не используется другим runtime.

## Запуск из PowerShell

После проверки keyring и явного выбора виртуального начального баланса:

```powershell
$env:TBOT_TRADING_MODE = 'paper'
$env:TBOT_CANDLE_MIN_INTERVAL_SEC = '0.1'  # переопределяет старое значение из .env/терминала
$env:TBOT_PAPER_STARTING_BALANCE = Read-Host 'Виртуальный начальный баланс (число, дробная часть через точку)'
$env:TBOT_DB_PATH = '.tmp-paper-network-check/tbot.db'
if (Test-Path $env:TBOT_DB_PATH) { throw 'Для первой проверки выберите новый путь БД; существующий файл не удалять' }
.\.venv\Scripts\python.exe -m trading_bot.main
```

Это настоящий длительный процесс, остановка — Ctrl+C. Не оставлять его работать
без контроля. Не запускать одновременно другой процесс с той же БД.
Ожидаемая остановка: один Ctrl+C → `event=tbot_stop_requested`, затем
`event=paper_bootstrap_cancelled stage=...` (если отмена внутри стадии) и
`event=tbot_stopped reason=operator_request`, exit 0. Bootstrap/feed/страницы и
ожидание квоты не начинают следующую работу; частичный пул не применяется.
Уже выполняющийся синхронный RPC может закончиться до обработки отмены; это не
гарантия немедленной отмены зависшего транспорта. Текущая paper-транзакция
завершается целиком. БД закрывается, отмена не пишется как отказ источника.
Первичный сбор 10 сессий широкого каталога может быть долгим. Решение оператора
2026-10-17 (+05): загрузка истории использует `TBOT_LIQUIDITY_WORKERS=4`, общий
лимитер MarketData — `TBOT_MARKET_DATA_REQUESTS_PER_MINUTE=600` за скользящие 60 с
для свечей/статусов/стаканов и повторов, с минимумом 0,1 с между стартами RPC.
Это перекрытие ожидания ответов, не 600 запросов на каждый worker. Повторное чтение
кандидатов с неполными 10 сессиями при новом 15-минутном слоте сохраняется.
`RESOURCE_EXHAUSTED`: максимум 61 попытка всего, пауза 1 с либо больше по server
reset; длинный конечный reset ожидается с возможностью отмены, не обрезается
старыми 120 секундами. `UNAVAILABLE` сохраняет отдельные 4 попытки, фиксированные
5 с и 120 с elapsed; auth/прочие статусы не повторяются. Это локальная политика
одного gateway, не обещанный срок API и не контроль чужих процессов/токенов.
При отказе дождись bounded retry/cooldown либо `paper_bootstrap_failed
stage=liquidity`; не запускай параллельно второй bootstrap.
При отказе процесса нет валидного пула; не считай исключённых из-за transport
тикеров низколиквидными.
Текущий `setup_logging` выводит технические логи только в stdout (терминал);
автоматической записи в `logs/` пока нет. SQLite-журнал решений и эпизодов источника
не является файлом технического лога. Не публиковать сырой вывод SDK.
Ошибка старта/источника должна быть видна как `action=stop` и ненулевой exit,
а отсутствие начального виртуального баланса — как `heartbeat-only`, **не** успешная проверка.
Автоматический каталог/история могут потребовать длительного чтения API; один
успешный поиск IMOEX ещё не подтверждает доступность свежих индексных свечей.

## Что фиксировать без секретов

- UTC начала/окончания, календарный день МСК, факт `paper` и sandbox target.
- Есть ли `paper_catalog`, `paper_liquidity_coverage`, `paper_pool_applied` с
  составом/причинами исключений и найденным ID IMOEX;
  есть ли heartbeat и реальные свежие закрытые бары. Стадии запуска —
  `paper_bootstrap_stage`; при отказе проверить `paper_bootstrap_failed stage=...`
  и `remedy`, не публикуя raw SDK traceback.
- Есть ли `decisions` с полным snapshot и `processing_state=complete`,
  а при отказе источника — `paper_source_episodes` с stage/error_type/action.
- Для повторного запуска той же тестовой БД: тот же закрытый бар не должен
  создавать второе решение/fill. `pending/failed` не исправлять автоматически:
  остановить runtime и использовать `MANUAL_PAPER_RECOVERY.md` после сверки.
- Отдельно: календарные отказы/защитное окно, отсутствие новых входов при
  неизвестном статусе, актуальность первого 10:00-бара для нового дня.
- Пересчёт локального режима в слотах расписания и лог смены. Наличие события
  не равно доставке VK: транспорт VK относится к M9 и пока не подключён.

Не считать успешный ответ одного RPC или один heartbeat приёмкой всего M7.
Сетевой обрыв/восстановление и полная сессия требуют самостоятельных наблюдений;
их нельзя выводить из одного успешного запуска.

## Состояние проверки 2026-10-16

В предыдущей проверке bootstrap был выключен, баланс отсутствовал; действовал
прежний ручной контракт кандидатов/пула/ID. В последующей локальной проверке
подтверждены `keyring.backends.Windows.WinVaultKeyring` и наличие записи
`broker_token` (без вывода значения). Это **не** проверка валидности токена,
принадлежности sandbox, TLS или доступности свечей. По последующему выводу
оператора: после настройки `GRPC_DEFAULT_SSL_ROOTS_FILE_PATH` TLS-ошибка ушла,
сбор дошёл до массовых `GetCandles`, затем получил `RESOURCE_EXHAUSTED`.
Прежняя реализация продолжала обход и исключала кандидатов после общей ошибки
квоты — такой пул нельзя считать проверенным. Оператор остановил процесс.
Полный сетевой runtime автоматического bootstrap ещё не подтверждён;
тесты на фикстурах не заменяют его.
Периодический пересмотр пула каждые 15 минут проверяется отдельно от bootstrap.

### Ограниченный read-only smoke 2026-10-16

После проверки SHA-256 официального корневого сертификата
`Russian_Trusted_Root_CA.pem` (совпадает с отпечатком в `docs/08_TINVEST_API.md`)
сертификат был указан через `GRPC_DEFAULT_SSL_ROOTS_FILE_PATH` только для процесса.
TLS verification оставалась включённой. Вызовы `InvestGateway` к sandbox вернули
каталог из 151 подходящей акции, статус SBER `SECURITY_TRADING_STATUS_NORMAL_TRADING`,
12 свечей 5m по SBER и 12 свечей 5m точного IMOEX. У обоих наборов последний
закрытый бар — `2026-10-16T11:35:00Z`; проверка после запроса показала возраст 355 с.

Сырые рыночные данные и результат проверки сохранены в `event_log` отдельной БД
`.tmp-paper-broker-smoke-4a6e65a623a2429d9db3dcb91f658834/tbot.db`;
`PRAGMA integrity_check=ok`, `trades=0`, `decisions=0`. Заявки и sandbox-счета
не запрашивались. Первый вызов с системным CA завершился TLS `UNAVAILABLE`; он
зафиксирован как неуспешный smoke, а не как отказ токена.

Это подтверждает получение реальных ответов через gateway и их запись в отдельный
SQLite `event_log`, но **не** полный `main → feed → PaperCycle` runtime. В рамках smoke
не выполнялись массовый 10-сессионный bootstrap, решения/эпизоды, quota recovery, restart/dedup,
внешняя отмена и длительная работа; в частности, этот smoke не подтверждает полную
приёмку M7.

### Полный запуск с балансом 10000 ₽: два отказа, приёмка заблокирована

`main.main()`, sandbox/gateway/feed/cycle без подмен данных. Локальная обвязка
проверяет isolation/effective Settings, сохраняет технический лог и ограничивает

В `11:57:53Z` однократный read-only запрос той же страницы LSNG

Ошибка другого инструмента не устанавливает точную сетевую причину. Третий
bootstrap до отдельной доработки не запускался. Production-код в этих двух
прогонах не менялся.

Parent read-only snapshot `12:13:49Z` и независимый QA `12:15:07Z`:
integrity ok, foreign_key_check без нарушений, миграции 1–10,
event_log/pool/decisions/trades/positions/source episodes/balance/anchors rows = 0,
pending/failed и duplicate-bar rows отсутствуют. Нулевая БД не доказывает
restart-dedup; успешный пул, decisions/episodes, clean-stop и рестарт работающего
runtime не проверены. Полная сетевая приёмка M7 **заблокирована**.

На момент этих двух прогонов gateway автоматически повторял только
`RESOURCE_EXHAUSTED`; `UNAVAILABLE` немедленно останавливал bootstrap. Затем
оператор поручил добавить ограниченный same-page retry `UNAVAILABLE` с сохранением
fail-closed и отмены. Новая реализация использует существующие budgets и не
подменяет историю, не отключает TLS и не разрешает бесконечные перезапуски.
Результаты последующего прогона фиксируются отдельно; прежние отказы не
считаются успешной приёмкой.

### Повтор после bounded UNAVAILABLE retry — bootstrap успешен, runtime остановлен

После локального RED→GREEN, независимого post-fix review (accepted) и
`make ci` (**1030 passed, 13 deselected**, ruff/black/mypy чисты) начат новый
ограниченный сетевой прогон `2026-10-16T15:15:52Z`. Новая отдельная БД:
`.tmp-paper-unavailable-20261016-10000-b7e2a9d1/tbot.db`; баланс **10000 ₽**,
paper/sandbox, 0,1 с pacing, 4 попытки / 5 с retry-base / 120 с elapsed на страницу.
Технический лог — `initial.log` в том же каталоге, deadline — 2700 с.

Preflight проверяет effective Settings, новый путь БД и официальный CA. Обвязка
не подменяет рыночные данные/стратегию/gateway; stopfile/deadline вызывает
production SIGINT handler, а не имитирует внешний консольный Ctrl+C.
Прогон завершён `2026-10-16T15:27:19Z`, exit **1**. Сбор каталога из 151
кандидата завершился: в `15:26:49Z` опубликован пул **21 бумага**, generation 1,
slot `15:15Z`, exact IMOEX ID `4821c9aa-36e8-4743-b37c-861e58581b25`.
SQLite содержит durable `pool_refresh_applied` с последними 10 датами сессий
02.10, 05–09.10 и 12–15.10. Сам факт публикации дополнительно подтверждён runtime-логом,
а не только SQL-before-publish intent.

Первый тик VTBR для 5m-бара `15:20Z` отклонён в `15:27:19Z`:
`higher_timeframe_stale / StaleDataError / stop`. Refusal сохранён в одном
`paper_source_episodes`, action=stop, status=open, attempt_count=1. Parent snapshot
`15:52:30Z` (`initial-stop.json`, SQLite mode=ro): integrity ok, FK без нарушений,
миграции 1–10, event_log=1, balances=1 (**paper 10000 ₽**),
decisions/trades/positions=0; duplicate bar keys отсутствуют. Это подтверждает
bootstrap и durable source-refusal, но не стратегическое решение или fill.

В полном логе нет событий `candle_request_unavailable`/`candle_request_quota`:
сетевой recovery новой retry-ветки в этом прогоне **не испытывался**. Clean SIGINT,
рестарт/dedup и периодический пересмотр пула не подтверждены. M7 открыт.

Найден отдельный риск проверки свежести (`paper_feed.py:976–990`): возраст
последнего старшего бара считается от открытия и сравнивается с
`duration + max_bar_staleness`. При дефолтном допуске 600 с в `15:27Z` даже
последний закрытый часовой бар `14:00Z` имеет возраст 87 минут и не проходит
порог 70 минут, хотя бар `15:00Z` ещё не закрыт. Это детерминированный возможный
ложный отказ; исходный лог не содержит timeframe/ts_open/age/limit отклонённого
старшего бара и не доказывает его фактический timestamp. Проверку/допуски не
меняли; повторный runtime не запускали. Следующий шаг — отдельная правка
семантики свежести с regression-тестами, без принятия незакрытых/действительно
пропущенных баров и без механического увеличения допуска.

### Повтор после исправления свежести HTF — HTF подтверждён, остановка на quote

По указанию оператора исправлена общая проверка 15m/1h тикера и закрытых баров
индекса: timestamp последнего закрытого бара должен совпасть с ожидаемым полным
интервалом обычной текущей сессии. Это не увеличение `PAPER_MAX_BAR_STALENESS_SEC`:
пропуск ожидаемого бара, незакрытые/будущие/смещённые данные не дают разрешение.
До первого закрытого интервала текущей сессии нового overnight-допуска нет;
пустая история тикера сохраняет `insufficient_history`, индекс — `chaos/paused`.
Новый `higher_timeframe_freshness` лог содержит instrument/timeframe,
source 5m, latest/expected open/close, lag, policy, reason/action.

Исходные public-feed регрессии 15:27/15:44 UTC: **2 failed → 2 passed**.
Новый модуль содержит 37 тестовых случаев, связанный набор — **328 passed**.
Финальный `make ci`: **1067 passed, 13 deselected**, Ruff/Black/mypy чисты;
независимый fixed-scope review accepted. Эти проверки offline, не сеть.

`runner.py restart --limit-sec 2700`, terminal 98. Используется прежняя

не рабочая БД; баланс 10000 ₽ и предыдущий source episode не сбрасываются.
Лог — `restart.log`, stopfile — `STOP-restart`; effective Settings/CA/path

integrity ok, FK без нарушений, миграции 1–10; pool events=2,

attempt_count=1), decisions/trades/positions=0. Сохранено `restart-stop.json`.

пустой baseline, **не доказательство replay-дедуп после исполнения**.
`UNAVAILABLE`/quota events в полном логе нет; network retry recovery не проверен.

Возможный отдельный дефект: `paper_feed.py:1099` сравнивает
`now` начала сборки тика с `quote.observed_at`, который gateway берёт из

«будущим» относительно старого now и дать отрицательный age. Но исходный лог не
содержит orderbook timestamp/age/receive time/limit; нельзя выбрать между этой
веткой и действительно старым стаканом (>30 с). Требуются диагностика и отдельная
проверка времени после RPC без расширения допуска или принятия реально будущих

## Пересмотр пула: отдельные наблюдения

Уточнение оператора: пересчёт круглосуточный (ночь/выходные включены), но это
не разрешение торговли вне обычной сессии. Проверять не только stdout, но и
versioned pool-события в `event_log` отдельной тестовой БД: applied/failed,
generation/slot/UTC-время, состав, instrument ID, session dates, причины.
Во время due/in-progress/failed нет новых входов по прошлому успешному пулу.
Открытые позиции сохраняют прежние ID и monitoring-only контекст.

В одном неизменном окне завершённых сессий повторный отбор должен читать
каталог и настоящий IMOEX, но не скачивать уже полностью проверенную историю заново.
По прямому указанию оператора 2026-10-17 (+05) кандидаты с неполными 10 сессиями
перечитываются в следующем 15-минутном слоте; отсутствие данных не кэшируется как успех.
При смене ID/лотности/дат/календаря кэш инвалидируется. Согласованное ограничение:
внутридневные исправления старой истории брокером без смены ключа не обнаруживаются;
после рестарта кэш холодный.

Отдельно наблюдать границу 15 минут, длительный пересчёт через несколько слотов,
квотный отказ без частичного пула, следующую попытку только в новом слоте,
отмену между страницами и отсутствие повторного fill после смены/возврата тикера.
При нескольких workers gateway читает постраничную историю кандидатов между
heartbeat, основной поток только опрашивает готовность и проверяет/публикует результат.
При одном worker сохранён cooperative page-path. Это не отменяет задержку собственных
синхронных RPC runtime и не доказывает непрерывный мониторинг M8.

Legacy-позиция без доказанного instrument ID в pool-журнале — основание остановить
запуск и выполнить отдельную сверку, не перепривязывать её по имени тикера.
CLI `paper_recovery confirm` исправляет только состояние claim после сверки,
не создаёт свидетельства identity и не чинит pool-журнал. Рабочую БД вручную
не менять ради обхода этого запрета.

## Измерение ускорения истории (2026-10-17)

Локальный wall-clock benchmark через настоящие gateway/feed с имитацией ответов SDK:

```powershell
.\.venv\Scripts\python.exe -m tests.benchmark_liquidity
```

Обе фазы читают одинаковое число страниц, меняется только число workers (1 и 4).
JSON содержит elapsed, фактические callback starts/second, peak in-flight, минимальное
расстояние между стартами и максимум стартов за скользящие 60 секунд. Первый импорт
SDK вынесен за измеряемые фазы; дополнительных warmup RPC нет. Это не сеть.

Для отдельного согласованного read-only sandbox-замера предусмотрен `--sandbox`
с обязательными `--instrument-id` (ранее проверенный ID), `--start` (aware ISO-время
начала целиком исторического диапазона) и `--pages` (1..60 на фазу). Используется
один gateway/общий лимитер, OS keyring и штатная проверка TLS; SQLite/позиции/заявки
не затрагиваются. Нельзя запускать одновременно с другим runtime на том же токене.
Общий жёсткий предел — 120 фактических callback-вызовов, включая retry обеих фаз.
Deadline 120 секунд кооперативный: он запрещает дальнейшую работу, но не прерывает
уже начатый синхронный RPC; без транспортного deadline зависший RPC может задержать
завершение. Не объявлять это жёстким wall-clock timeout или полной сетевой приёмкой M7.
