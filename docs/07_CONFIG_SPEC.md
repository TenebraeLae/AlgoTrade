# 07_CONFIG_SPEC — все параметры

Конфиг загружается один раз, валидируется, передаётся в конструкторы.
Магических чисел в коде нет. Неизвестный параметр в конфиге = ошибка запуска,
а не тихое игнорирование. Битый конфиг = режим `paper` + лимиты по умолчанию.

Решение оператора 2026-10-16: paper-bootstrap автоматически получает каталог
подходящих MOEX-акций и проверенный источник настоящего IMOEX через API.
Каталог ограничен обычными/привилегированными RUB-акциями MOEX, не OTC,
не qualified-only, с доступными API-покупкой/продажей и полными лотом/квантом/сектором.
Дублирующиеся тикеры исключаются; соответствие ticker→instrument ID для открытых
позиций фиксируется отдельно от обновляемого каталога и сохраняется в pool-журнале.
Переназначение тикера другому ID не должно перенаправлять сопровождение позиции.
Статический статус каталога не заменяет свежую проверку статуса перед входом.
Кандидаты ранжируются по среднему сессионному объёму за последние одинаковые
для всех 10 завершённых подтверждённых календарём торговых сессий, строго выше
40-го перцентиля; выбранный пул применяется автоматически без ручного утверждения.
Пропущенную недавнюю сессию нельзя заменить более старой. Состав и причины
исключений журналируются (`paper_catalog`, `paper_liquidity_coverage`, `paper_pool_applied`).
Открытые позиции вне выбранного пула сохраняются в контексте счёта и получают
monitoring-only тики без новых входов; breadth считается только по выбранному пулу.
Это не реализация автоматического закрытия/стоп-мониторинга M8.
Такая же автоматизация обязательна для будущего live; сам live этим не разрешён.
Без `PAPER_STARTING_BALANCE` запуск остаётся heartbeat-only, без выдуманного
капитала и сетевых запросов. При заданном балансе отсутствие токена, неоднозначный
или отсутствующий IMOEX, недостаточный пул и непроверенная история дают явный
отказ, а не переход к ручным тикерам или другой бумаге вместо индекса.
Для стандартных `POOL_MIN=15` и `LIQUIDITY_PERCENTILE=0.40` требуется достаточно
кандидатов, чтобы после строгого отсечения осталось минимум 15 (при разных
объёмах — не менее 25). Устаревшие три поля не разрешают обойти автоотбор.
Автоматический bootstrap при старте не равен периодическому пересмотру пула.
Решение оператора 2026-10-16: фиксированный интервал 15 минут
(`config.DEFAULT_POOL_REFRESH_MIN`) задаёт **круглосуточные** слоты, включая ночь
и выходные; обычные календарные/статусные запреты торговли не меняются.
Это не настраиваемое поле `Settings`: `TBOT_POOL_REFRESH_MIN` не поддерживается
и, как любой неизвестный параметр, вызывает явную ошибку конфигурации.
Поздний запуск обслуживает текущий слот; пропущенные слоты не проигрываются.
Пока обновление требуется, выполняется или завершилось отказом, новые входы
запрещены; открытые позиции сохраняют pinned identity и monitoring-only контекст.

Проверенные объёмы завершённых сессий переиспользуются в памяти с ключом:
`instrument ID + lot size + ordered session dates + calendar fingerprint + version`.
При изменении ключа история читается заново; ошибки/неполные данные не становятся
успешным кэшем. Каталог и exact IMOEX проверяются на каждом пересмотре. Политика
осознанно не обнаруживает внутридневные исправления брокером старой истории;
после рестарта кэш холодный. При `LIQUIDITY_WORKERS>1` workers читают полную
постраничную историю ограниченного числа кандидатов между тактами runtime;
основной поток неблокирующе опрашивает готовность и сам проверяет/применяет результат.
Нет ожидания следующего heartbeat перед каждой страницей. При `LIQUIDITY_WORKERS=1`
сохранён последовательный cooperative page-path. Каталог/поиск индекса и собственные
синхронные RPC runtime всё ещё могут задержать такт; жёсткая непрерывность мониторинга
не обещается. Уже начатый sync RPC может завершиться после отмены.

Новый состав применяется целиком после durable-записи в существующий `event_log`;
SQL-ошибка останавливает runtime. Смена пула не пересоздаёт feed, не стирает ack,
не завершает claims и не меняет учёт/риск. После отказа новая попытка — следующий
слот, не немедленный бесконечный retry. При рестарте позиции без доказуемой
сохранённой identity требуют явной сверки, а не догадки по имени тикера.
Допуски свежести — консервативная политика paper-источника, а не обещанные
пределы задержки T-Invest API. Значения должны быть положительными; 5m-бар
проверяется от открытия по прежнему `PAPER_MAX_BAR_STALENESS_SEC`. По указанию
оператора 2026-10-16 старшие 15m/1h бары тикера и контекст индекса сверяются с
**последним ожидаемым полностью закрытым баром**, а не с фиксированным возрастом
от открытия. Сетка привязана к обычной сессии 10:00–23:40 МСК; берётся последний
полный интервал, завершившийся не позже времени наблюдения. До первого полного
интервала текущей сессии прежняя история не получает нового допуска overnight;
неподтверждённый календарный день также не даёт свежий контекст. Публикационный
лаг не разрешает использовать предыдущий бар вместо уже ожидаемого нового:
пропуск, смещённая сетка, будущий/незакрытый бар дают fail-closed. Допуски 5m и
стакана не увеличиваются. Пустая история 15m/1h по-прежнему даёт журналируемый
`insufficient_history`; непустая устаревшая история блокирует построение тика.
Недоступный/устаревший индекс остаётся `chaos/paused`, без кэширования разрешения.
Диагностика свежести содержит timeframe, фактические/ожидаемые open/close,
время наблюдения, возраст/отставание, политику и причину отказа. Состояние инструмента читается один раз при построении тика;
недоступный статус не считается нормальными торгами. Возраст стакана считается
от локального времени **после возврата RPC**, а не от начала сборки тика:
`response_received_at − quote.observed_at`. `PAPER_MAX_QUOTE_STALENESS_SEC=30`
не увеличивается; допустимы ровно 0 и 30 секунд, отрицательный возраст и превышение
лимита запрещены. Наивные timestamps и откат локальных часов до/во время RPC
не дают разрешение. Диагностика показывает tick-start, request-start, response,
broker timestamp, возраст, лимит и reason/action, без сырого SDK-исключения.
Таймстемпы свечей/strategy snapshot не переносятся вперёд для обхода свежести;
ответ не должен оживлять истёкший 5m/HTF/календарный допуск.
Если рынок не даёт достаточно свежих данных, paper-цикл отказывает, а не
ослабляет допуски автоматически. Эта проверка не обещает неограниченный срок
годности стакана после последующих RPC и не заменяет проверки исполнения M8.

`REGIME_REFRESH_MIN` (`TBOT_REGIME_REFRESH_MIN` для окружения) задаёт интервал
локального классификатора каждого тикера. Это не TTL разрешения на вход:
свежесть текущей истории и доступность контекста проверяются независимо.
Глобальная защита IMOEX chaos/breadth не ждёт следующего локального слота.
Календарь загружается из поставляемого `data_seed/holidays_ru.md`; поддержано
только подтверждённое покрытие 2026, вне него отказ. Пропавший/пустой/битый seed
останавливает bootstrap. Спецсессии и выходные не разрешаются по NORMAL_TRADING.
Инструкция настоящего сетевого прогона: `PAPER_RUNTIME_VERIFICATION.md`.

В штатном `main()` оператор задаёт `TBOT_PAPER_STARTING_BALANCE`;
кандидаты, рабочий пул и ID IMOEX определяются автоматически. Секрет берётся
**только** из OS keyring (`service=tbot`, `name=broker_token`,
`security.get_stored_token`) без приглашения ввода. Новый токен нужно отдельно
сохранить оператору в keyring целевой среды; опубликованный в переписке токен
подлежит отзыву. Шлюз для чтения подключается только к sandbox target;
проверка TLS не отключается. Если корневой сертификат не входит в доверенные
gRPC-корни окружения, перед запуском требуется штатная переменная процесса
`GRPC_DEFAULT_SSL_ROOTS_FILE_PATH` с проверенным сертификатом (см. `08_TINVEST_API.md`).
Отсутствие ключа, недоступная история или повреждённые якоря — отказ запуска,
а не тихий heartbeat как при **отсутствующем** bootstrap.

## Данные и API
```
RATE_LIMIT_BUDGET=TODO(VERIFY)        # точная общая квота — проверить; не угадывать
RATE_LIMIT_SOFT_STOP=0.8
BACKOFF_BASE_SEC=5 BACKOFF_MAX_ATTEMPTS=10
STREAM_RECONNECT_SEC=5
CANDLE_MIN_INTERVAL_SEC=0.1          # минимальный интервал стартов unary MarketData, не время RPC
CANDLE_MAX_ATTEMPTS=4                # отдельный bounded UNAVAILABLE budget
CANDLE_RETRY_BASE_SEC=5.0            # фиксированный UNAVAILABLE retry, не quota
CANDLE_MAX_RETRY_WAIT_SEC=120.0      # UNAVAILABLE elapsed budget; не обрезает quota reset
CANDLE_QUOTA_MAX_ATTEMPTS=61         # 1..61 фактическая попытка действия всего, включая mixed statuses
MARKET_DATA_REQUESTS_PER_MINUTE=600  # общий локальный потолок MarketData за скользящие 60 с; 1..600
LIQUIDITY_WORKERS=4                  # ограниченное перекрытие RPC history; 1..32
CACHE_TTL_5m=по свече, 15m=до конца 15м, 1h=до конца часа
POSITION_POLL_SEC=2.5
```

Все поля читаются с префиксом `TBOT_`; durations конечные и положительные,
попытки положительные (quota ≤61), `LIQUIDITY_WORKERS` — 1..32, локальный минутный бюджет —
1..600. Политика gateway неизменяема после запуска. Решение оператора
2026-10-17 (+05): общий thread-safe monotonic admission для всех фактических unary
MarketData RPC этого gateway (свечи, статусы, стаканы, включая повторные попытки):
не более `MARKET_DATA_REQUESTS_PER_MINUTE` стартов в любом скользящем окне 60 с.
Учёт намеренно консервативный: pending/in-flight вызов удерживает lease без истечения,
а после завершения кредит учитывается ещё 60 с. Поэтому latency и задержка планировщика
не освобождают квоту раньше фактического вызова; реальная скорость может быть немного
ниже 600/мин. Lease освобождается через finally, pacing/cooldown повторно проверяются
перед dispatch. Минимальный интервал 0,1 с распространяется на старты; ожидание ответа не держит
lock лимитера. `LIQUIDITY_WORKERS` ограничивает конкурентную загрузку истории,
не умножая общий бюджет. Проверка свечей/staging/SQLite/publication остаётся
на owner-thread; workers не торгуют и не используют SQLite. Повторное чтение
неполных 10 сессий при новом 15-минутном слоте сохраняется, отрицательного кэша нет.
Это локальная политика одного gateway, не гарантия динамической квоты тарифа,
общих расходов других процессов/токенов/счетов либо общего IP-лимита.

Квотная политика `RESOURCE_EXHAUSTED`: максимум `CANDLE_QUOTA_MAX_ATTEMPTS`
попыток всего, по умолчанию 61; пауза минимум 1 секунда, при положительном
server `ratelimit_reset` — не меньше указанного числа относительных секунд.
Некорректный/отсутствующий reset не становится бесконечным cooldown. Длинный
конечный reset ожидается с возможностью отмены, а не отклоняется из-за старых
120 секунд. Cooldown общий для ожидающих MarketData-вызовов; уже начатые RPC
могут завершиться. `UNAVAILABLE` сохраняет отдельную ограниченную политику
4 попытки/5 секунд/120 секунд elapsed без quota reset hint. Успешные страницы
не перечитываются из-за retry текущей страницы. Исчерпание UNAVAILABLE даёт
`CandleRequestError`, квоты — `CandleQuotaExhaustedError`. Авторизационные и
прочие статусы (например, `INTERNAL`, `NOT_FOUND`) не повторяются. UNAVAILABLE
не доказывает причину транспорта/TLS; bounded retry не исправляет trust.
Ни один общий отказ не превращается в «тикер без истории» или частичный пул.
SIGINT/SIGTERM передают однонаправленную отмену `CancellationToken` в bootstrap,
feed и `CandleRequestTiming`. До/после RPC и страниц проверяется остановка;
ожидания используют короткие Event.wait-части (≤0,1 с), чтобы Python в Windows
мог обработать сигнал. `OperationCancelled` — штатная остановка с INFO/exit 0,
не ошибка источника, не exclusion тикера и не повод применить частичный пул.
Уже начатый синхронный RPC может завершиться; новые после проверки отмены не
запускаются. Текущая транзакция paper-исполнения не прерывается проверками отмены.
См. `08_TINVEST_API.md` для внешней квоты и оговорок.

## Обязательные тесты конфига
1. Битый YAML/нет файла → `paper` + дефолтные лимиты, не падение и не «undefined».
2. Неизвестный ключ → явная ошибка с именем ключа.
3. `RISK_PER_TRADE > 0.02` → предупреждение в лог и VK (не отказ, но заметно).
4. `TRADING_MODE=live` вне торгового окна → отказ старта live с объяснением.
5. Смена любого параметра из списка «Риск» через публичный API бота отсутствует (см. 04_RISK).
