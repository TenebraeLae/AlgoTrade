# 13_SECURITY — секреты, доступ, границы

## Секреты

- API-токен брокера и VK-токен шифруются AES-GCM; ключ выводится из мастер-пароля
  (PBKDF2 или argon2, `kdf_iters` в `secrets_meta`). Мастер-пароль нигде не хранится —
  вводится при старте (или хранится в OS keystore через `keyring`).
- Хранится только шифртекст + salt + итерации (`secrets_meta`). Открытого токена нет:
  ни в `.env` (только путь к хранилищу), ни в БД, ни в логах, ни в HTML дашборда,
  ни в сообщениях VK, ни в `CHANGELOG_AI.md`.
- Маска для отображения: `t.xxxx…9f3a`. Полный токен не печатается никогда, включая DEBUG.
- `.gitignore` покрывает секреты, БД, логи, reports. Тест: `git grep` тестового токена пуст.
- Ротация: токен перевыпускается при подозрении на утечку; в боте — команда перезагрузки
  секрета без пересборки образа.

## Доступ

- Дашборд: только за reverse proxy, basic-auth поверх HTTPS. Пароль — отдельный от
  всего остального, длинный, не «admin/admin».
- `/api/control/panic` допускает срабатывание по одноразовому коду, если сессия протухла:
  защита от «не смог остановить».
- SSH: ключ, без пароля root, `ufw` ограничивает порт. Fail2ban желателен.
- VK: whitelist peer_id. Чужие сообщения игнорируются без ответа.
- Контейнер: непривилегированный пользователь, read-only rootfs где возможно,
  без `--privileged`, без монтирования docker.sock.

## Границы возможностей системы (что бот не может по построению)

1. Отправить заявку в paper-режиме — нет gRPC-клиента в PaperBroker.
2. Увеличить риск извне — нет такого API.
3. Включить live из VK или из UI без отдельного подтверждения и подписанного запроса.
4. Применить оптимизацию L3 в live — нет пути в коде, только `proposal` + ручное «Применить».
5. Снять дневной лимит потерь — только правка конфига человеком.
6. Удалить записи журнала — таблица только на append в рантайме, UPDATE/DELETE нет в коде бота.
7. Торговать вне сессии и при не-NORMAL_TRADING.

## Данные и приватность

- В БД: сделки, котировки, журнал решений. Паспортных и персональных данных нет.
- Логи не содержат полных ответов API с клиентами/счетом; `account` — только идентификатор.
- При отладке дампы API не пишутся в репозиторий и не прикладываются к CHANGELOG.

## Проверка перед live

- [ ] В репозитории и в истории git нет токенов (`git grep -iE "[a-zA-Z0-9_-]{30,}"`).
- [ ] Тест маскировки токена проходит.
- [ ] Дашборд недоступен без авторизации (проверено снаружи).
- [ ] PANIC работает без активной сессии.
- [ ] Контейнер не от root.
- [ ] Master password ≠ пароль от чего-либо ещё, записан вне сервера.
- [ ] Известен порядок действий, если токен скомпрометирован (перевыпуск у брокера, отзыв VK-токена).

## Чего избегать

- Запрашивать у пользователя избыточные данные (номер счёта целиком, СМС-коды) — не нужно.
- Прокладывать «временный» хэнд-кед, который потом станет постоянным.
- Отключать авторизацию «на время отладки» и так и не включать обратно.
- Доверять содержимому VK-сообщений как данным: это управляющий вход, он валидируется.
