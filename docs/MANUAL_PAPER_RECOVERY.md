# Ручная офлайн-сверка paper `pending` / `failed` (M7)

Это **ручное признание одного бара завершённым или пропущенным**, а не повтор
исполнения. CLI не создаёт fill, не удаляет решение, не исправляет сделки,
позиции, баланс, стопы, параметры риска, якоря капитала или дневные стопы.
`complete` после этой процедуры означает «оператор принял исход бара», а не
«машина доказала корректность всего FIFO/денежного учёта».

## Обязательный порядок: сначала остановка

1. Остановить **все** процессы/контейнеры paper-runtime и его автоматический
   перезапуск (service manager, supervisor, restart policy, scheduler). Проверить,
   что старый процесс действительно завершился. Не подтверждать решение во время
   исполнения или зависшего fill. Не запускать второй экземпляр CLI параллельно.
2. Сохранить согласованную резервную копию SQLite штатным SQLite backup-механизмом;
   при копировании файлов учитывать WAL/SHM, не копировать только основной файл
   работающей БД. Убедиться в правильном пути к рабочей paper-БД.
3. Обновить приложение и применить штатные миграции **офлайн** через существующий
   механизм `database.apply_migrations` / `database.connect`. Нужны 0006–0008 и
   `0010_paper_manual_reconciliation.sql` (0009 — независимые категории фильтров).
   Сам recovery CLI **не применяет миграции**, не создаёт БД/каталоги и не чинит схему.
4. Выполнить `inspect`, сверить данные, затем отдельно выполнить `confirm`.

**Граница гарантии:** `--runtime-stopped` — подтверждение человека, не детектор
живого процесса. SQLite lock не может остановить runtime, который уже получил
`pending` и ждёт fill вне транзакции. Если он продолжит после подтверждения,
возможна запись сделки старым процессом. Поэтому stop-first обязателен. CLI не
подключается к сети, SDK, брокеру, keyring, VK или системному менеджеру процессов.

## Inspect — только чтение

```text
python -m trading_bot.paper_recovery inspect --db PATH --decision-id N
```

`PATH` должен указывать на существующий файл SQLite, `N` — положительный id
paper-решения. Несуществующая БД не открывается с созданием; live-решение
отклоняется. Чтение идёт в одной read-only SQLite-транзакции, без миграций.
Можно посмотреть также `complete`, но подтвердить его повторно нельзя.

JSON содержит `fingerprint` (SHA-256 канонического JSON снимка) и `snapshot`:

- полную выбранную строку `decision`, включая bar-key и прежнее состояние;
- все `linked_trades` по `trades.journal_id`, **без фильтра режима**, чтобы
  несогласованную live-связь нельзя было скрыть;
- все `paper_positions` и открытые FIFO-строки `paper_open_trades`;
- полный `paper_trade_journal` по возрастанию id — все paper-сделки, включая
  старые закрытые строки, не связанные с выбранным claim;
- `paper_balances`, последнюю paper-строку по id и счётчики истории сделок;
- все `equity_anchors`, `daily_stop_latches`, миграционный `recovery_meta`;
- все остальные `unresolved_claims` и применённые `schema_versions`.

Деньги сохраняются Decimal-текстом; недопустимые типы чисел не нормализуются
молча. Снимок содержит локальные учётные данные: обращаться с ним как с приватным
журналом, не публиковать его целиком. Инструмент не принимает новый свободный
текст; секреты не должны находиться и в исходной БД.

Fingerprint охватывает весь paper-журнал: даже правка старой посторонней закрытой
FIFO-строки требует повторной сверки. Снимок читается и сериализуется целиком,
без пагинации: память, размер вывода/аудита и время удержания lock растут с историей.
Это осознанный простой контракт для ручной офлайн-процедуры; на большой БД заранее
оценить ресурсы, свободное место и длительность обслуживания. Нельзя обрезать
журнал ради уменьшения снимка или подтверждать только выбранную страницу.

## Что оператор проверяет вручную

- Правильные БД, id, тикер, сторона и закрытый 5m-bar-key UTC.
- Связанные сделки: отсутствие/наличие fill, фактические лоты, лотность, стоимость,
  комиссии/проскальзывание и состояние каждой FIFO-порции. У частичного fill
  остаток **не доисполняется**.
- Все paper-позиции и их соответствие журналу, включая стопы/тейки и чужие
  открытые порции. Никакие уровни не должны ослабляться этой процедурой.
- Свободный paper-баланс по полному денежному учёту, якоря и историю дневных стопов.
  Сам CLI не пересчитывает FIFO/P&L и не доказывает баланс на произвольной истории.
- Нет ещё работающего runtime или неясного результата операции. При расхождении
  **не подтверждать**, сохранить evidence и отдельно разбирать учёт. В CLI нет
  команды коррекции, очистки latch или автоматического ремонта.

## Confirm — отдельное явное решение оператора

Команда ниже записана одной строкой для переносимости между shell:

```text
python -m trading_bot.paper_recovery confirm --db PATH --decision-id N --operator operator_17 --expected-fingerprint SHA256_FROM_INSPECT --outcome no_fill --runtime-stopped --trades-reviewed --positions-reviewed --balance-reviewed
```

Все четыре флага обязательны и означают, что проверки **уже сделаны**, а не
просьбу выполнить их. `operator` — несекретный локальный псевдоним: ASCII-буква,
далее буквы/цифры/`_`/`-`, всего 1–32 символа. Это атрибуция, не аутентификация;
доступ к файлу ограничивается правами ОС. Не использовать токен, пароль, email
или текст заметки. `--notes` и другие свободные поля не поддерживаются;
ошибочные CLI-аргументы не отражаются в диагностике.

Допустимы ровно два `--outcome`:

- `no_fill`: оператор установил, что fill не было, и **пропускает** этот бар.
  CLI запрещает исход при любых связанных trades (включая закрытые/live) или
  связанной paper-позиции. Отсутствие trades само по себе не доказывает баланс:
  ручная сверка всё равно обязательна.
- `accepted_existing_fill`: оператор принимает **существующее** исполнение.
  CLI требует signal со стороной, связанные trades того же режима/тикера/стороны,
  положительные целые lots/lot_size, конечную положительную цену, неотрицательные
  издержки, допустимые статусы и сумму лотов не выше разрешённого `size_lots`.
  Открытые порции выбранного тикера должны совпасть с одной paper-позицией по
  стороне/лотам; полностью закрытые порции не требуют текущей позиции. Когда
  **во всей paper-истории нет закрытий**, проверяется совпадение свободного баланса
  с `balance_after` последней строки. При закрытиях это сравнение непригодно:
  FIFO меняет старые id. Полная денежная/FIFO-сверка остаётся обязанностью человека.

Под `BEGIN IMMEDIATE` CLI **заново** читает весь снимок, сверяет fingerprint и
только затем в одной транзакции добавляет строку аудита и меняет одну строку
`pending/failed → complete`. На любой ошибке обе записи откатываются. Изменение
снимка другим соединением (включая чужой claim, баланс, позицию, anchor/latch)
делает fingerprint устаревшим. Нужно повторить inspect **и ручные проверки**,
а не автоматически подставлять новый hash.

## Аудит, перезапуск и ошибки

Миграция 0010 создаёт `paper_manual_reconciliations`: UNIQUE `decision_id`,
`previous_state`, UTC `ts`, `operator`, `fingerprint`, JSON `confirmations`,
`outcome` и полный **предшествующий** JSON `snapshot`. UPDATE/DELETE аудита
запрещены триггерами. Это локальный append-only журнал, не криптографическая
защита от владельца SQLite-файла. Успешный confirm печатает id и `complete`.

Exit codes: `0` — результат зафиксирован/снимок прочитан; `1` — отказ сверки,
устаревший snapshot, ошибка локальной БД/доступа/блокировки (операция остановлена);
`2` — некорректная CLI-команда. Автоматического retry нет. SQL-ошибка выводится
без сырого текста БД, с UTC, decision id и типом; разобраться в причине локально
и заново inspect. Если миграция отсутствует, confirm не создаёт таблицу сам.

После принятия **всех** pending/failed можно отдельно запустить runtime.
Любой оставшийся paper-claim по-прежнему блокирует `PaperCycle` глобально.
На повторном баре executor видит прежний `complete` и не создаёт второе решение
или fill. Source-эпизоды эта ручная команда не закрывает. Повторный confirm
того же id отклоняется; старое evidence не переписывается.

Проверки: `tests/test_manual_reconciliation.py` использует реальную SQLite,
два соединения, actual PaperCycle/restart, сбой после commit частичного long/short
fill, stale hash, ошибку SQL с откатом аудита, запреты входа/режима/исхода и
неизменность учёта/стопов/якорей/latches. Сетевой runtime и полноценный FIFO-аудит
этими тестами не объявляются проверенными.
